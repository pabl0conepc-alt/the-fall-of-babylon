# Architecture

## Current implementation

The package uses explicit contracts, ports, engines, and an orchestrator:

- `domain/contracts.py` defines immutable requests, evidence records, byte-range provenance, findings, recovery status, engine results, and JSON job reports.
- `ports.py` defines the `Analyzer` and `AnalysisEngine` interfaces.
- `local_analysis.py` securely opens one local regular file and acquires at most 1 MiB in bounded chunks while hashing it. POSIX uses no-follow directory descriptors; Windows uses handle-relative opens that reject reparse points for single-file analysis.
- `directory_analysis.py` traverses local directories through no-follow directory descriptors, records rejected entries, and delegates regular files to the same safe reader and engines.
- `engines.py` provides deterministic built-in engines for signature-family identification, byte-frequency profiling, and streaming encoding validation.
- `native/` contains the C++17 parser and its CMake/CTest suite. `native_parser.py` sends the already acquired bytes to the bundled helper over stdin and validates its bounded response; the helper has no source path, filesystem, or network interface.
- `orchestrator.py` registers a fixed ordered engine set, acquires the file once, and runs each engine against the same immutable evidence digest.
- `report_store.py` optionally saves complete versioned JSON reports in a local SQLite database using parameterized SQL and transactions; list/export access is read-only.
- `render.py` presents file, directory, and saved-job reports as human-readable terminal output without changing their JSON schema.
- `web.py` serves the offline browser interface on IPv4 loopback only; it validates Host, Origin, a per-server request token, and upload size before passing selected bytes through the same analysis core.
- `web/index.html` contains the self-hosted, responsive interface; it uses only the browser's explicit single-file picker, offers transient results and a user-triggered JSON download, and loads no remote assets.
- `cli.py` requires an authorization basis for command-line analysis, renders text by default, and supports `--format json` for automation.
- `tests/` covers contracts, safe file and directory access, provenance, engine orchestration, SQLite storage/migration, CLI behavior, browser upload/server boundaries, and the native parser adapter. `native/tests/` exercises synthetic C++ fixtures through CTest.

The domain layer has no filesystem or process side effects. The local analysis layer rejects `..`, symlinks/reparse points, non-regular files, files over 1 MiB, and files that change while being read. POSIX file and directory access uses no-follow descriptors. Windows single-file analysis uses handle-relative opens and rejects reparse points; directory traversal remains unavailable on Windows because its walker requires POSIX descriptor APIs. The payload is held in memory only for bounded analysis (at most 1 MiB in Python and one bounded helper input buffer); the native parser has a short timeout and fixed output fields. Built-in analysis performs no regex, decompression, or sample execution.

File reports record a job ID, UTC acquisition time, source path, byte count, SHA-256, acquisition method, and `recovery_status: not_attempted`. Findings reference the artifact digest, byte range, method, and observation. The signature engine recognizes PDF, PNG, JPEG, GIF, ZIP, GZIP, SQLite, WAVE, WebP, ELF, Mach-O, and PE header signatures; an extension without a matching signature is only a hint. The C++ engine validates bounded PE/COFF headers and sections, ELF32/64 headers and program/section tables, and Mach-O thin/universal headers, load commands, and slice ranges. It checks offsets, counts, sizes, and arithmetic before reading; truncated, malformed, and unsupported structures are reported as parse states, not as security judgments. The byte-profile engine reports Shannon entropy, printable ASCII byte count, and NUL byte count; the encoding engine checks strict UTF-8 or BOM-indicated UTF-16/32 validity incrementally. Neither emits literal source content.

Directory reports record entries up to explicit limits and contain per-file reports only for regular files that pass the existing no-follow reader. Symlinks and special entries are never opened; exceeded depth/file/byte/entry caps are explicit and set the report's `truncated` flag. The CLI requires a non-empty caller-supplied authorization statement but cannot independently verify authorization. Reports omit the statement itself and print to stdout; they are not persisted unless `analyze --database PATH` or `analyze-directory --database PATH` is explicitly supplied. The browser interface requires an explicit authorization checkbox and applies the same per-file size ceiling; it writes upload bytes to a mode-`0600` file inside a private temporary directory and removes that directory after generating the response. The report's displayed path is only the selected filename, not the temporary server path.

The SQLite store uses application ID `0x42414259` and schema version 2, migrating version 1 file-report databases transactionally when the next report is saved. It stores file or directory report JSON and searchable job metadata in one transaction. A new database is created with mode `0600` on POSIX; pre-existing databases must be regular files with no group/other permissions. Existing unversioned databases containing user objects and databases with unknown application/schema versions are refused. A database must not be any analyzed file or be located inside the directory being inventoried. No parent directories are created. `jobs` and `export` open the database read-only, use bound parameters, and never write. The report store is local only; it performs no network access.

Directory traversal ceilings are depth 3 below root, 50 regular files, 100 recorded entries, 1 MiB per file, and 16 MiB total acquired bytes. Traversal uses `os.scandir` on an opened directory descriptor, reads entry metadata without following symlinks, and opens child directories with `O_NOFOLLOW`. Each regular file is subsequently re-opened through the existing no-follow reader before analysis.

The browser server never accepts a local filesystem path from a request, binds to `127.0.0.1`, requires an exact loopback Host and same-origin upload with a per-process token, rejects transfer-encoded or oversized request bodies, and sets no CORS allowance. It does not initialize the SQLite report store or save results; only the browser's explicit JSON download persists a report at the user's direction.

## Scope boundary

This implementation performs only structural metadata parsing for PE, ELF, and Mach-O; it does not disassemble code, list/extract archives, decompress, recover deleted data, decompile, execute samples, scan websites/targets, provide phishing intelligence, exploit, or reconstruct projects. Directory inventory is limited to the explicitly selected local directory and the fixed traversal bounds above and is unavailable on Windows. Persistence is opt-in and limited to the caller-selected local SQLite database; callers may also redirect stdout themselves. Dynamic analysis remains blocked until a separately designed and tested sandbox exists. Any future capability must be isolated behind the domain contracts and added only with explicit scope and safety review.
